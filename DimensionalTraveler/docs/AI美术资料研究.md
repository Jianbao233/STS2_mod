## 1. 证据规则

### 1.1 真源与优先级

发生冲突时，按以下顺序裁决：

1. 当前运行游戏及实机截图；
2. `SL2_v0.109.0` 中被场景、模型或导入元数据实际引用的资源；
3. 同版本 DLL 反编译的加载、注入和显示代码；
4. `DimensionalTraveler` 当前源码；
5. `SL2_v0.108` 近版对照；
6. 教程、外部资料、设计文档和推断。

当前资源快照为 `K:\杀戮尖塔mod制作\SL2_v0.109.0`。其中 GDRE 记录为 15,705 个提取文件、4,002 个转换资源，且有 23 个脚本反编译失败。因此：场景、图片、`.tres`、可读取 C# 与 DLL 反编译可作为证据；依赖失败脚本的结论必须标记为待验证。

### 1.2 证据等级

| 等级 | 含义 | 能否形成生产约束 |
|---|---|---|
| A | 当前 `v0.109.0` 场景、模型、原图或运行时链路直接证实 | 可以，但只限已覆盖的资产职责 |
| B | 当前项目源码直接证实的现状或占位状态 | 可以形成项目范围和替换前提，不能代替游戏规格 |
| C | `v0.108` 近版对照或外部方法资料 | 不能单独形成规格 |
| D | 合理推断、待测路径或尚未读取的资源 | 不能用于正式交付 |

### 1.3 资产记录模板

每个资产结论必须包含：用途、实际资源路径、模型/场景引用链、原始像素与 Alpha、导入设置、显示容器、叠层/遮罩、安全区、交付物、证据等级、版本日期与待验证项。缺项时标记为待验证，禁止按文件名或教程补全。

## 2. 当前项目的资产缺口

`DimensionalTraveler` 当前已完成玩法内容，但尚未接入正式表现资源。

| 项目事实 | 证据 | 影响 |
|---|---|---|
| 卡牌模板目前使用 `CardModel.MissingPortraitPath` | `src/Content/`、`src/Alchemy/` 共 17 个文件、37 处匹配 | 当前卡图是占位资源；任何新卡图都需要后续显式替换资源路径 |
| 9 个药剂家族是战斗内卡牌，而非原生药水 | `src/Content/Cards/Potions/AlchemyPotionCard.cs` | 药剂卡图与原生药水瓶图是不同资产类型，不能互相替代 |
| 六种炼金原理当前复用三张原版能量图标 | `src/Resources/AlchemyPrinciples.cs` | 原理图标尚未具备六类独立视觉编码；未来替换须同时覆盖小/大图路径 |
| 遗物、Epoch、事件、战斗角色与表现资源属于后续阶段 | `README.md`、`核心设计文档.md` | 本轮不虚构不存在的资源目录、尺寸或加载代码 |

结论：本轮首要产物是规格、资产清单和验证方法；**不是**向游戏目录投放 PNG，也不是批量生成卡图。

## 3. 首轮原生资源审计表

### 3.1 普通卡牌内部插画

| 字段 | 已证实事实 |
|---|---|
| 资产职责 | 卡牌插画只负责内部肖像/场景，不负责卡框、标题、费用、描述、类型牌或稀有度 UI。 |
| 模型路径 | `CardModel.PortraitPath` 指向 `res://images/atlases/card_atlas.sprites/<卡池>/<卡牌>.tres`；原始 PNG 路径为 `res://images/packed/card_portraits/<卡池>/<卡牌>.png`。 |
| 显示链 | `NCard` 创建 `300×422` 容器；`card.tscn` 的 `Portrait` 固定显示区为 `250×190`，在独立 `PortraitCanvasGroup` 中；`NCard.UpdatePortrait()` 单独注入 `Model.Portrait`、边框、标题条及卡框。 |
| 原版样本 | `bash.png` 原图为 `1000×760`、无 Alpha；对应 `bash.tres` 图集区域为 `250×190`。 |
| 导入 | 样本 `bash.png.import` 为非 VRAM 压缩、无 MipMap。 |
| 遮挡/安全区 | 插画可视框为 `250×190`；其上叠加 `PortraitBorder`，外层另有标题条、费用图标、描述文本与类型牌。边框内的精确不透明覆盖范围尚未量化。 |
| 生图约束 | 输出画面本体；禁止烘焙完整卡框、标题、费用、描述、类型、稀有度、水印或可读文字。构图必须接受 `250×190` 裁切/缩放。 |
| 等级 | A |

**证据链**

```text
CardModel.PortraitPath
→ images/atlases/card_atlas.sprites/.../*.tres
→ images/atlases/card_atlas_*.png 的 250×190 区域
→ NCard.UpdatePortrait()
→ scenes/cards/card.tscn / Portrait(250×190)
→ NCard.defaultSize(300×422)
```

## 4. 当前可执行的交付边界

以下是首轮审计后唯一可写入 Brief 的硬约束：

1. **卡图**：母图可保留高分辨率，但最终画面须适配 `250×190`；只交内部插画，UI 由原生卡牌场景注入。
2. **遗物**：小图、轮廓、大图是不同职责；大图样本为 `256×256`，小图最终容器为 `60×60`。
3. **原生药水**：小图/轮廓/大图分层；大图样本为 `256×256`，腰带容器为 `60×60`。
4. **Power**：小图最终显示区为 `40×40`，大图样本为 `256×256` 且用于 VFX；不得把数字画进图。
5. **角色选择图**：原版样本 `132×195`，最终受 `88×130` Mask 裁切；透明主体、无 UI。
6. **所有非 UI 插画**：禁止绘入文字、水印、卡框、按钮、费用、标题条、稀有度或数值。

这些约束不等于“已经授权正式生成”。身份、视觉方向、样本分析与对象级 Brief 仍缺失。

## 5. 原版样本分析规范

分析必须先直接读取图片，并按资产类别分别记录：

- 轮廓和缩略识别；
- 主体占比、焦点和留白；
- 线条、色块、光影、材质、背景噪声；
- Alpha 边缘、Outline 与小尺寸阅读结果；
- 同类样本共有特征和单图例外；
- 可观察、可复核的描述。

禁止事项：

- 用文件名、卡牌描述或艺术家姓名代替视觉观察；
- 把一个 `256×256` 图标的规律推广到卡图或角色图；
- 用“杀戮尖塔风格”作为未拆解的 Prompt；
- 使用在世艺术家姓名作为风格代理。

### 下一批样本

| 类别 | 最少样本 | 检验问题 |
|---|---:|---|
| 卡图 | 6 张，覆盖攻击/技能/能力与不同角色 | `250×190` 内焦点、背景与边框遮挡的关系 |
| 遗物 | 6 件，含高轮廓和低轮廓对象 | `60×60` 下的剪影、Outline 与大图一致性 |
| 药水 | 6 瓶，含透明瓶、实体瓶、复杂内容物 | 小图/大图的可读信息如何取舍 |
| Power | 6 个增益/减益 | `40×40` 下颜色、形状和数字区的避让 |
| 角色选择 | 5 个角色图 | `88×130` Mask 中的身形、头部与关键器具安全区 |
| 战斗角色 | 至少 1 个原版角色完整视觉场景 | 动画状态、纹理分层、锚点与地面安全区 |

## 6. 外部方法资料的地位

ComfyUI、Krita、iLab、模型文档、社区案例和旧教程可用于研究：参考职责分离、母图管理、局部编辑、元数据留档与人工修图；但它们不是当前游戏的规格证据。

任何模型、供应商、成本、Prompt 语法、目录结构或生图参数，都必须在本账本的对应资产通过审计、用户确认视觉方向后，才可进入生产规范。
